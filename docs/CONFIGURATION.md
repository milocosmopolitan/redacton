# Terminal configuration

The configuration UX is tested on the terminal combination in [compatibility](COMPATIBILITY.md). Desktop rendering and interception remain separate gates; this document does not announce Desktop support. Existing `/redacton` and `/redactoff` behavior is unchanged.

## Commands and local edits

`/redact:status` shows requested protection, cached readiness and its observation time, coverage, custom-rule count, safe IDs, configuration source/revision and recent fixed outcomes. It does not call the helper, restart scanning, write settings or check current health. Zero findings does not mean safe content.

`/redact:config`, `/redact:add-rule` and `/redact:remove-rule` open local panels. **Management commands take no arguments. Never paste credentials, patterns or test text into slash-command arguments: the host can store submitted arguments before local rejection.** Put rule fields in the local form only after its keyboard-focus indicator confirms focus. Close the panel before ordinary chat; composer submissions are withheld while it is open, including OFF. That guard does not prevent the host storing mistakenly submitted composer text. Use Validate → Preview → Apply session; Save personal and project review/trust/save are separate explicit actions. Cancel and Revert are local controls. A draft must pass the pinned engine's validation, then a synthetic preview, before explicit Apply. Until then, the previous configuration protects operations. Preview is non-enforcing and does not measure accuracy. Invalid, cancelled and stale changes leave active settings unchanged.

Editing an existing user rule reuses the guided fields and stages one atomic replacement, rejecting missing or duplicate IDs. Changes to inherited personal/project rules become an explicit session override; saving remains separate. Cancelling retains the previous active rule. Removal lists only user rules. Built-ins cannot be removed; their overlap can still match a removed custom format. Removing the last custom rule omits the engine ruleset. Revert/undo checks the current revision, so a later change cannot be overwritten silently.

## Guided rules

A token rule uses a unique safe lowercase ID, a literal 3–64-byte prefix, one supported alphabet, an exact or at-least run of 1–4096 characters, contextual/entropy specificity, and either no validator or trailing-lower-hex validation. Available alphabets are `alnum`, `alnum-dash`, `alnum-dash-dot`, `upper-alnum`, `digit`, `lower-hex` and `base64-body`. The core parser, not a Mod detector, validates the compiled recipe.

An assignment-name rule uses ambiguous names. Matching depends on the engine's context/entropy conditions; every assigned value is not guaranteed to match. Pinned beta.14 reports one shared names detector, so **all names rules must use the same action**. New names rules default to the existing shared action. The explicit “Action for all assignment-name rules” control changes their actions together in one candidate; token actions remain unchanged. Imported mixed names actions are rejected. Token rules may independently redact or block. Built-in overlap can win; inspect the actual preview action before applying.

Custom actions are redact or block only. There are no allow/warn exceptions, built-in exclusions, arbitrary regex/code, PII or exact-secret registration. Baseline credentials redact and recognized private keys block. At most 64 user rules and 32 raw assignment names are accepted. The pinned baseline scanner rejects recognizable credential literals in prefixes, IDs and names before activation or saving. **Never paste actual credential values:** unknown internal credentials cannot be universally recognized, and a format definition can itself be sensitive.

## Scope and saving

Approved layers replace the entire custom-rule list: product defaults → personal → project → session. Arrays are not merged. An empty higher layer intentionally replaces lower custom rules; it never disables the built-in protection floor. Operations capture an immutable configuration together with ON/OFF before work starts.

Session edits are temporary. Saving personal defaults or project settings is explicit. Personal defaults are restored before the first supported operation in a new/restored/branched session; an explicit personal reload imports a later validated file revision. Project settings still require local review and exact-document trust. An existing session override remains higher priority when a saved layer is loaded. A loaded project candidate cannot become active until its exact scope identity and revision are reviewed and trusted in the current session. Restart/restore/branch starts requested ON and requires project trust again; OFF, drafts, recent input and history are never saved.

Personal data lives in `~/.config/redacton/settings.json`; project data lives in `.redacton/settings.json` under the current trusted project root. Explicit import/export uses a separate `transfer.json` file in the selected personal or project scope. Its portable document contains only schema version and rule definitions, without scope identity, revisions, OFF or history. Import stages a candidate for review, project trust when applicable, core validation, synthetic preview and explicit session Apply; saving it is a separate action. Export requires confirmation because internal formats can be sensitive. There is no arbitrary-path file importer. Saved settings and transfer documents are bounded to **65,536 UTF-8 bytes**. Saved documents use schema version 1; unknown versions are rejected instead of silently migrated. The helper writes only validated declarative settings, using a scope lock, revision check and atomic replacement. A conflict, corruption or permission error is visible and does not activate the failed candidate. Cancelling an edit before apply/save changes nothing; closing a form cannot promise rollback of an already dispatched durable write. Reset clears the selected scope's custom list by saving an empty document; it does not silently reset other scopes. Concurrent changes require a fresh review.

Configuration fields and preview samples stay out of model messages by design. That does not establish that every host UI input is absent from host storage. Actual persistence/privacy evidence is recorded separately in [compatibility](COMPATIBILITY.md); original prompts and tool arguments may remain in host history.

## Interrupted-save recovery

Normal dead-owner recovery is automatic. If a helper dies while holding the recovery claim, a later save can return `SETTINGS_BUSY` until manual repair. Close all Claude sessions using that scope. Inspect only `.settings.lock` metadata; if its recorded PID still exists, leave everything unchanged. With sessions closed and that PID verified nonexistent, remove only `.recover-<same nonce>` and retry Save. Preserve `settings.json`, `transfer.json` and `.identity`. If the lease or nonce is malformed/unverifiable, leave it untouched and request support.
