# Terminal UI investigation

Claude Code 2.1.294 on macOS ARM64, synthetic isolated configuration only. No real user auth/config/transcripts were read, no paid model call was used, and test configuration/processes were removed after each run.

## Actual screen-reader terminal evidence

`rtk proxy python3 qualification/terminal-ui-alternative.py` launches an argv-only Claude child attached to a PTY. The internal direct child is necessary because `rtk proxy` captures child output and otherwise switches Claude to noninteractive print mode. The shell entrypoint still uses RTK.

The isolated test reaches two independent yes/no menus: workspace trust and confirmation of the synthetic environment API key. Sending a character and carriage return in one write was unreliable: the application sometimes read an empty answer. Sending `y`, waiting 150 ms, then carriage return advanced both menus. An empty answer can be retried without modifying the user's configuration.

With the supported `--ax-screen-reader` flag, an actual interactive session showed the Redacton ON/loading line before the prompt. `/redactoff` then produced the immediate warning and an OFF warning directly above the next input prompt. The test typed a synthetic draft while OFF; that draft appeared after the warning. The observed fixed metadata was:

```json
{
  "renderer": "screen-reader",
  "offCommandSent": true,
  "immediateWarningObserved": true,
  "persistentWarningObserved": true,
  "typedWhileOff": true,
  "warningRedrawnDuringTyping": false,
  "onboardingBlocked": false
}
```

Screen-reader mode emits sequential text instead of in-place redraws. This proves visible warning output at the next prompt in that mode, with subsequent typed input; it does not prove a normal renderer keeps a warning pinned during arbitrary scrolling/tool activity. No screenshot or raw terminal transcript is committed. The probe retains text transiently for fixed marker checks and emits safe observations only.

Anthropic's [screen-reader guide](https://support.claude.com/en/articles/15924927-use-claude-code-cli-with-a-screen-reader) documents the flag, sequential presentation, and yes/no menu input. The installed CLI help independently lists the flag.

## SDK-supported fallback candidates

The host-generated `claude-code/index.d.ts` says `$.ui.status(text)` keeps one plugin-owned line under the prompt until it is replaced or cleared. This is a simpler candidate fallback than JSX rendering, but its visible behavior must still be exercised on the target renderer; this investigation did not paint a status line.

`$.ui.notice(tool_use_id, text)` is tied to an open tool dialog and is removed when that call resolves. It cannot serve as a persistent OFF warning on an idle prompt.

The existing `ui.render` AbovePrompt tree is accepted by the local SDK tests and was actually emitted by the screen-reader terminal test. SDK acceptance alone did not prove visible output; the PTY run supplies the separate screen-reader evidence. The official [Mod reference](https://code.claude.com/docs/en/plugins/mods/reference) directs implementers to the declarations generated by their installed host when public snapshots differ.

## Normal-renderer follow-up

The actual normal trust menu was not numbered: No, exit was selected by default, with Yes below it. DownArrow and a separate Enter, after a one-second input-readiness wait, advanced it. A transient pyte screen emulator then verified the OFF warning after typing, its removal on ON, and restoration on repeated OFF. See [actual normal-terminal evidence and exclusions](ui-report.md). Screen-reader evidence does not stand in for normal rendering, and neither run qualifies Desktop or model-driven tool activity.
